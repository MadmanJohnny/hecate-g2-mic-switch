# 原理与实测记录

本文记录这套方案是怎么一步步试出来的，包含所有关键实测数据。
如果你想知道"为什么不能直接用那个 HID 报告判断"，答案在这里。

---

## 一、被测设备

| 项目 | 值 |
|---|---|
| 设备名 | HECATE G2 GAMING HEADSET |
| USB VID:PID | `VID_2D99&PID_0026` |
| 接口 MI_00 | 音频功能，由官方驱动 `oem1.inf` 接管（服务名 `HECATEG2_SERVICE`，C-Media 方案，带音效 APO） |
| 接口 MI_03 | USB Input Device → HID 子设备 `HID\VID_2D99&PID_0026&MI_03` |
| HID 顶层用法 | Usage Page `0x0C`（Consumer）/ Usage `0x01`（Consumer Control） |
| 输入报告长度 | 5 字节 |

也就是说，线控开关不是"哑开关"，它挂在一个 **HID 消费类控制接口**上。

---

## 二、HID 抓包：能收到事件，但**分不出方向**

直接打开 HID 接口读取输入报告（见 `tools/hid_probe.py watch`），
拨动开关时抓到的原始数据只有两种：

```
00 08 00 00 00    ← 按键按下
00 00 00 00 00    ← 按键松开
```

关键观察：

1. **每一次物理拨动都产生一模一样的一对**，拨到"开"和拨到"静音"没有任何差别。
   累计抓取 17 次拨动，逐字节比对全部相同。
2. 报告里其余 3 个字节恒为 `00`。
3. HID 能力查询显示 `FeatureReportByteLength = 0`，也就是说读不到"状态"类报告。
4. 设备重新枚举（拔插耳机）时**不会**主动发送一帧表示当前开关位置。

结论：这是个**瞬时"点击"事件**，语义等价于键盘上按一下某个键。
它只能告诉你"有人拨了一下开关"，不能告诉你"现在开关在哪一边"。

> ⚠️ 这正是本项目 v1 会"用着用着就反了"的根本原因：只能统计拨动次数，
> 一旦在程序没监听时拨过开关（例如拔插耳机的 20 秒里），
> 计数就永久错位一位。

原始报告的含义（16 位逻辑值按位排列）：

```
字节 0  字节 1  字节 2  字节 3  字节 4
 00     08      00      00      00
        └─ bit3 置 1 = 按钮按下
```

## 三、系统音频栈是否知道这个开关？——**不知道**

有人会想：那读 Windows 里麦克风的"静音"状态不就行了？

于是用 Core Audio（`IAudioEndpointVolume::GetMute`）盯住该耳机的录音端点，
全程 150 ms 轮询，同时反复拨动开关。

**结果：静音标志始终是 `False`，一次都没变。**

说明静音是在耳机芯片内部完成的（或根本没有走系统的静音通道），
Windows 音频栈完全不知道这个开关的存在。

所以"读系统静音状态"这条路是死的，只能靠实际采集到的信号。

---

## 四、麦克风信号是否真的被切断？——**是的，而且非常干净**

用 `waveIn` 打开默认录音设备，每 150 ms 采一段并统计峰值：

| 开关位置 | 峰值 | RMS | 非零采样点 |
|---|---|---|---|
| **静音** | **1** | 0.5 | 554 / 1600 |
| 麦克风开（环境安静） | 200 – 300 | 45 – 55 | ~7900 / 8000 |
| 麦克风开（正常说话） | 600 – 7400 | 80 – 340 | ~7900 / 8000 |

静音时信号是**完全死寂**的（只剩 1 LSB 的直流偏置），
与开启时相差 **25 倍以上**。

判定阈值取 `8` 时：静音侧余量 8 倍，开启侧余量 25 倍，非常稳。

> 踩过的坑：第一次做这个测量时，45 秒采样窗口里电平始终在 200–500 波动，
> 看起来"静音没有作用"。查日志才发现那段时间**用户根本没拨开关**，
> 采到的全是同一个位置的数据。做这类测量一定要把
> "操作时间线"和"数据时间线"对齐确认
> （后来为此写了 `tools/diag_test.py`，把 HID 事件和音频电平打在同一张时间线上）。

## 五、微信输入法这条链路

要让开关驱动语音输入，得先搞清楚微信输入法 Windows 版的语音输入是怎么触发的。
用 `SendInput` 注入不同按键组合，并从三个角度判定是否真的开始录音：
窗口是否出现、麦克风占用记录是否刷新、录音开始/停止时间。

| 测试 | 结果 |
|---|---|
| 模拟按住**右 Alt** 4 秒 | ❌ 无效（右 Alt 在 Windows 版不是语音输入键） |
| 模拟**单击** Ctrl+Win 80 ms | ❌ 无效 |
| 模拟**按住 Ctrl+Win** 2 秒 | ✅ 录音 `05:00:18` 开始、`05:00:20` 结束 —— 正好是松开的时刻 |
| 模拟**按住 Ctrl+Win** 4 秒 | ✅ 弹出 `wetype.flutter.setting / '语音输入'` 窗口，麦克风占用记录实时刷新 |

结论：

1. Windows 版微信输入法的语音输入是 **长按 `Ctrl+Win` 说话**（不是单击切换）；
2. 它**不过滤模拟按键**，可以用程序代按。

第 1 点很重要：因为它是长按模式，程序必须在整个语音输入期间**真的按住**
这两个键 —— 这就是"说话时敲键盘会带上 Win 修饰键"这个副作用的来源。

## 六、最终方案

```
拨动线控开关
   ↓ 一帧 HID 报告 00 08 00 00 00（只当触发器，不当状态）
收到报告
   ↓ 等待 60ms 让硬件切换稳定
采集 150ms 麦克风信号，量峰值
   ├─ 峰值 ≤ 8   → 开关在「静音」  → 松开 Ctrl+Win（停止语音输入）
   └─ 峰值 > 8   → 开关在「麦克风开」→ 按住 Ctrl+Win（开始语音输入）
```

因为状态是"量"出来的而不是"数"出来的：

- 拔插耳机、漏掉事件 → 下一次拨动依然能正确判断方向；
- 一次拨动产生两个事件 → 两次量到同一状态，第二次被判为"位置未变化"直接忽略；
- 程序重启 → 启动时先实测一次，直接得到当前位置。

## 七、复现 / 自查方法

仓库自带全部探测脚本，换耳机或换电脑时可以重跑一遍：

```bash
# 1) 看 HID 接口能力与支持的 usage
python tools/hid_probe.py caps

# 2) 抓 HID 报告（拨动开关，看是否收到 00 08 00 00 00）
python tools/hid_probe.py watch 0

# 3) 实时麦克风电平（拨动开关，看静音时峰值是否掉到个位数）
python src/mic_level.py 30 400

# 4) HID 事件 + 音频电平 同一条时间线
python tools/diag_test.py 45

# 5) Core Audio 静音状态是否随开关变化
pwsh -File tools/mute_probe.ps1 -Match HECATE -Seconds 120

# 6) 某个按键组合能否触发目标软件
python tools/key_combo_test.py "ctrl+win" 240 4
```

第 3 步是判断"这款耳机适不适用"的关键：如果拨到静音时峰值仍然有几百，
说明它的静音不是硬件切断信号，本方案不适用。
